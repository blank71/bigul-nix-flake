\section{Decidable partiality}
\label{sec:partiality}

The bidirectional transformations discussed in this paper are ``decidably partial''.
By ``decidable partiality'' we mean that the transformations are actually total functions which wrap their results in the standard \ensuremath{\protect\hyperlink{M4d61796265}{\constructor{Maybe}}} datatype:%
\footnote{An \Agda\ datatype is defined by listing all of its constructors along with their types in full.
A datatype can be \emph{parametrised}, as in the case of \ensuremath{\protect\hyperlink{M4d61796265}{\constructor{Maybe}}}, which has a parameter \ensuremath{\identifier{A}\;{:}\;\constructor{Set}}, specified between the name of the datatype and the colon on the first line.
(\ensuremath{\constructor{Set}} is the type of all (small) types.)
Parameters can be referred to throughout a datatype definition.}

The result of a piece of successful computation is wrapped in the \ensuremath{\protect\hyperlink{J6a757374}{\constructor{just}}} constructor, while failed computation is represented by \ensuremath{\protect\hyperlink{N6e6f7468696e67}{\constructor{nothing}}}.
The behaviour of decidably partial functions is different from the usual partial functions as formalised in terms of complete partial orders (see, e.g., Gibbons~\cite{Gibbons-calculating-functional-programs}):
In \autoref{sec:view-case} we will need to define programs that produce some result or fail respectively when a sub-program fails or produces some result, but this is not possible in the setting of complete partial orders (since such functions violate monotonicity, a necessary condition for computability).

We can choose to write our decidably partial bidirectional transformations directly as \ensuremath{\protect\hyperlink{M4d61796265}{\constructor{Maybe}}}-programs, but when proving their well-behavedness, we will need to analyse or establish how a piece of decidably partial computation succeeds or fails, and the task would be much easier if the computation steps leading to success or failure are reified as data.
(An example of such proofs is given in the definition of lens composition~\ensuremath{\protect\hyperlink{_5f21945f}{\anonymous {\scalebox{.75}[1]{$\leftrightarrow$}}\kern-\underscorespace\anonymous }} in \autoref{sec:BX}.)
The reification starts from the following datatype \ensuremath{\protect\hyperlink{P506172}{\constructor{Par}}}, which is a deep embedding of the combinators that we will use for writing decidably partial programs:%
\footnote{Here the datatype \ensuremath{\protect\hyperlink{P506172}{\constructor{Par}}} is \emph{indexed} by \ensuremath{\constructor{Set}} (which appears to the right of the colon on the first line), meaning that \ensuremath{\protect\hyperlink{P506172}{\constructor{Par}}} is in fact a \ensuremath{\constructor{Set}}-indexed family of simultaneously defined types.\par
As for the constructors, let us look at the simplest case, \ensuremath{\protect\hyperlink{F6661696c}{\constructor{fail}}}:
The constructor \ensuremath{\protect\hyperlink{F6661696c}{\constructor{fail}}} constructs a value of type \ensuremath{\protect\hyperlink{P506172}{\constructor{Par}}\;\identifier{A}} for any \ensuremath{\identifier{A}\;{:}\;\constructor{Set}}.
There is thus one argument to \ensuremath{\protect\hyperlink{F6661696c}{\constructor{fail}}}, namely \ensuremath{\identifier{A}\;{:}\;\constructor{Set}}, and the type of \ensuremath{\protect\hyperlink{F6661696c}{\constructor{fail}}}'s result depends on the value of this argument (which happens to be a type).
This is an example of \emph{dependent function types}, whose result type can depend on the value of the argument.
Logically, dependent function types are read as universally quantified propositions --- the dependent function type \ensuremath{\{\mskip1.5mu \identifier{x}\;{:}\;\identifier{A}\mskip1.5mu\}\;\identifier{→}\;\identifier{B}\;\identifier{x}} is read as ``for all \ensuremath{\identifier{x}\;{:}\;\identifier{A}} the property~\ensuremath{\identifier{B}} holds for~\ensuremath{\identifier{x}}''.
(Ordinary function types, on the other hand, denote implications logically.)\par
Back to \ensuremath{\protect\hyperlink{F6661696c}{\constructor{fail}}}: most of the time \Agda\ can infer what \ensuremath{\protect\hyperlink{F6661696c}{\constructor{fail}}}'s argument should be based on how \ensuremath{\protect\hyperlink{F6661696c}{\constructor{fail}}} is used, so we make the argument \emph{implicit} by enclosing it in curly brackets.
(Explicit arguments, on the other hand, are enclosed in round brackets.)
We can then invoke \ensuremath{\protect\hyperlink{F6661696c}{\constructor{fail}}} without supplying the argument, leaving it for \Agda\ to infer.
We de-emphasise implicit arguments typographically when they cause visual annoyance, as in this case.\par
An \Agda\ name can be used as an infix (or, in general, mixfix) operator when the name contains underscores, in which case the underscores indicate where the arguments should go.
For example, we can apply \ensuremath{\protect\hyperlink{_5f3e3e3d5f}{\anonymous {\bind }\kern-\underscorespace\anonymous }} to arguments \ensuremath{\identifier{mx}}~and~\ensuremath{\identifier{f}} by writing either \ensuremath{\protect\hyperlink{_5f3e3e3d5f}{\anonymous {\bind }\kern-\underscorespace\anonymous }\;\identifier{mx}\;\identifier{f}} or \ensuremath{\identifier{mx}\;\protect\hyperlink{_5f3e3e3d5f}{\bind }\;\identifier{f}}.}

Informally:
A value of type \ensuremath{\protect\hyperlink{P506172}{\constructor{Par}}\;\identifier{A}} represents a piece of decidably partial computation that either successfully produces a value of type~\ensuremath{\identifier{A}} or fails.
The first two constructors \ensuremath{\protect\hyperlink{R72657475726e}{\constructor{return}}} and \ensuremath{\protect\hyperlink{_5f3e3e3d5f}{\anonymous {\bind }\kern-\underscorespace\anonymous }} represent the usual monadic operators~\cite{Moggi-monads,Wadler-essence}, and \ensuremath{\protect\hyperlink{F6661696c}{\constructor{fail}}} indicates failed computation.
We will also need error handling, which is represented by the \ensuremath{\protect\hyperlink{C6361746368}{\constructor{catch}}} constructor.
The behaviour of our \ensuremath{\protect\hyperlink{C6361746368}{\constructor{catch}}} is slightly different from the usual one: execution of \ensuremath{\protect\hyperlink{C6361746368}{\constructor{catch}}\;\identifier{mx}\;\identifier{f}\;\identifier{my}} binds the result of~\ensuremath{\identifier{mx}} to~\ensuremath{\identifier{f}} if \ensuremath{\identifier{mx}}~computes successfully, or goes to execution of~\ensuremath{\identifier{my}} if \ensuremath{\identifier{mx}}~fails to compute.
Also we will frequently need to ensure that a \ensuremath{\constructor{Bool}} value is \ensuremath{\constructor{true}} before continuing with the rest of a program, so the constructor \ensuremath{\protect\hyperlink{A6173736572745f7468656e5f}{\constructor{assert}\anonymous \constructor{then}\kern-\underscorespace\anonymous }} is included for convenience --- execution of \ensuremath{\protect\hyperlink{A6173736572745f7468656e5f}{\constructor{assert}}\;\identifier{b}\;\protect\hyperlink{A6173736572745f7468656e5f}{\constructor{then}}\;\identifier{p}} becomes execution of~\ensuremath{\identifier{p}} when \ensuremath{\identifier{b}}~is \ensuremath{\constructor{true}}, or fails otherwise.

Formally, the meaning of the constructors of \ensuremath{\protect\hyperlink{P506172}{\constructor{Par}}} is given by the interpreter \ensuremath{\protect\hyperlink{R72756e506172}{\identifier{runPar}}\;{:}\;\{\mskip1.5mu \identifier{A}\;{:}\;\constructor{Set}\mskip1.5mu\}\;\identifier{→}\;\protect\hyperlink{P506172}{\constructor{Par}}\;\identifier{A}\;\identifier{→}\;\protect\hyperlink{M4d61796265}{\constructor{Maybe}}\;\identifier{A}} shown in \autoref{fig:runPar}.
We say that \ensuremath{\identifier{mx}\;{:}\;\protect\hyperlink{P506172}{\constructor{Par}}\;\identifier{A}} computes to \ensuremath{\identifier{x}\;{:}\;\identifier{A}} exactly when \ensuremath{\protect\hyperlink{R72756e506172}{\identifier{runPar}}\;\identifier{mx}\;\protect\hyperlink{_5f22615f}{\identifier{≡}}\;\protect\hyperlink{J6a757374}{\constructor{just}}\;\identifier{x}}, and that \ensuremath{\identifier{mx}}~fails to compute exactly when \ensuremath{\protect\hyperlink{R72756e506172}{\identifier{runPar}}\;\identifier{mx}\;\protect\hyperlink{_5f22615f}{\identifier{≡}}\;\protect\hyperlink{N6e6f7468696e67}{\constructor{nothing}}}.
These two equalities are what we aim to reify as data next.

Our reification of decidably partial computation as the datatype \ensuremath{\protect\hyperlink{P506172}{\constructor{Par}}} and \Agda's support of full dependent types allow us to compute for any \ensuremath{\identifier{mx}\;{:}\;\protect\hyperlink{P506172}{\constructor{Par}}\;\identifier{A}} and \ensuremath{\identifier{x}\;{:}\;\identifier{A}} a type \ensuremath{\identifier{mx}\;\protect\hyperlink{_5f21a65f}{\mathrel{\mapsto}}\;\identifier{x}} whose inhabitants explain how \ensuremath{\identifier{mx}}~computes to~\ensuremath{\identifier{x}} step by step.
The definition of this family of types is shown in \autoref{fig:CompSeq}:%
\footnote{The type \ensuremath{\raisebox{\ht\strutbox}{\hypertarget{_22a4}{}}\identifier{⊤}\index{_22a4@\ensuremath{\identifier{⊤}}}\;{:}\;\constructor{Set}} has exactly one constructor \ensuremath{\constructor{tt}\;{:}\;\protect\hyperlink{_22a4}{\identifier{⊤}}}, while the type \ensuremath{\raisebox{\ht\strutbox}{\hypertarget{_22a5}{}}\identifier{⊥}\index{_22a5@\ensuremath{\identifier{⊥}}}\;{:}\;\constructor{Set}} has no inhabitant --- logically they are read as truth and falsity respectively.
The type family \ensuremath{\raisebox{\ht\strutbox}{\hypertarget{_5f22615f}{}}\anonymous \kern\underscorespace{\identifier{≡}}\anonymous \index{_5f22615f@\ensuremath{\anonymous \kern\underscorespace{\identifier{≡}}\anonymous }}\;{:}\;\{\mskip1.5mu \identifier{A}\;{:}\;\constructor{Set}\mskip1.5mu\}\;\identifier{→}\;\identifier{A}\;\identifier{→}\;\identifier{A}\;\identifier{→}\;\constructor{Set}} is defined such that \ensuremath{\identifier{x}\;\protect\hyperlink{_5f22615f}{\identifier{≡}}\;\identifier{y}} is inhabited if and only if \ensuremath{\identifier{x}}~and~\ensuremath{\identifier{y}} are equal.
The type former \ensuremath{\raisebox{\ht\strutbox}{\hypertarget{_5f228e5f}{}}\anonymous \kern\underscorespace{\mathrel{\uplus}}\anonymous \index{_5f228e5f@\ensuremath{\anonymous \kern\underscorespace{\mathrel{\uplus}}\anonymous }}\;{:}\;\constructor{Set}\;\identifier{→}\;\constructor{Set}\;\identifier{→}\;\constructor{Set}} is disjoint union (disjunction) whose constructors are \ensuremath{\constructor{inj_1}\;{:}\;{}^{\color{gray}\{\mskip1.5mu \identifier{A}\;\identifier{B}\;{:}\;\constructor{Set}\mskip1.5mu\}\;\identifier{→}}\;\identifier{A}\;\identifier{→}\;\identifier{A}\;\protect\hyperlink{_5f228e5f}{\mathrel{\uplus}}\;\identifier{B}} and \ensuremath{\constructor{inj_2}\;{:}\;{}^{\color{gray}\{\mskip1.5mu \identifier{A}\;\identifier{B}\;{:}\;\constructor{Set}\mskip1.5mu\}\;\identifier{→}}\;\identifier{B}\;\identifier{→}\;\identifier{A}\;\protect\hyperlink{_5f228e5f}{\mathrel{\uplus}}\;\identifier{B}}, and the type former \ensuremath{\raisebox{\ht\strutbox}{\hypertarget{_5fd75f}{}}\anonymous {\identifier{×}}\kern-\underscorespace\anonymous \index{_5fd75f@\ensuremath{\anonymous {\identifier{×}}\kern-\underscorespace\anonymous }}\;{:}\;\constructor{Set}\;\identifier{→}\;\constructor{Set}\;\identifier{→}\;\constructor{Set}} is cartesian product (conjunction), whose constructor is~\ensuremath{\anonymous \kern\underscorespace\identifier{,}\anonymous }\kern1pt.
The symbol~`\ensuremath{\protect\hyperlink{_5fd75f}{\identifier{×}}}' is also overloaded to denote \emph{dependent pair types} --- the inhabitants of a dependent pair type \ensuremath{(\identifier{x}\;{:}\;\identifier{A})\;\protect\hyperlink{_5fd75f}{\identifier{×}}\;\identifier{B}\;\identifier{x}} are pairs where the type of the second component depends on the value of the first component.
Logically, dependent pair types are read as existentially quantified propositions --- \ensuremath{(\identifier{x}\;{:}\;\identifier{A})\;\protect\hyperlink{_5fd75f}{\identifier{×}}\;\identifier{B}\;\identifier{x}} is read as ``there exists \ensuremath{\identifier{x}\;{:}\;\identifier{A}} such that the property~\ensuremath{\identifier{B}} holds for~\ensuremath{\identifier{x}}''.\par
An underscore in a right-hand side expression instructs \Agda\ to infer what should be placed there.}
\ensuremath{\protect\hyperlink{R72657475726e}{\constructor{return}}\;\identifier{x}} computes to~\ensuremath{\identifier{x'}} when \ensuremath{\identifier{x}}~is exactly~\ensuremath{\identifier{x'}}, and \ensuremath{\identifier{mx}\;\protect\hyperlink{_5f3e3e3d5f}{\bind }\;\identifier{f}} computes to~\ensuremath{\identifier{y}} when there exists \ensuremath{\identifier{x}\;{:}\;\identifier{A}} such that \ensuremath{\identifier{mx}}~computes to~\ensuremath{\identifier{x}} and \ensuremath{\identifier{f}\;\identifier{x}} computes to~\ensuremath{\identifier{y}}, and so on.
Here our use of the term ``computes to'' is justified, since we can prove that
\[ \ensuremath{\identifier{mx}\;\protect\hyperlink{_5f21a65f}{\mathrel{\mapsto}}\;\identifier{x}} \qquad\text{and}\qquad \ensuremath{\protect\hyperlink{R72756e506172}{\identifier{runPar}}\;\identifier{mx}\;\protect\hyperlink{_5f22615f}{\identifier{≡}}\;\protect\hyperlink{J6a757374}{\constructor{just}}\;\identifier{x}} \]
are equivalent.
That is, a term of type \ensuremath{\identifier{mx}\;\protect\hyperlink{_5f21a65f}{\mathrel{\mapsto}}\;\identifier{x}} can be constructed if and only if \ensuremath{\protect\hyperlink{R72756e506172}{\identifier{runPar}}\;\identifier{mx}\;\protect\hyperlink{_5f22615f}{\identifier{≡}}\;\protect\hyperlink{J6a757374}{\constructor{just}}\;\identifier{x}}, meaning that our reification of \ensuremath{\protect\hyperlink{R72756e506172}{\identifier{runPar}}\;\identifier{mx}\;\protect\hyperlink{_5f22615f}{\identifier{≡}}\;\protect\hyperlink{J6a757374}{\constructor{just}}\;\identifier{x}} as \ensuremath{\identifier{mx}\;\protect\hyperlink{_5f21a65f}{\mathrel{\mapsto}}\;\identifier{x}} is accurate.
In the clause for \ensuremath{\protect\hyperlink{C6361746368}{\constructor{catch}}\;\identifier{mx}\;\identifier{f}\;\identifier{my}}, a possible situation for the computation to succeed is when \ensuremath{\identifier{mx}}~fails but \ensuremath{\identifier{my}}~succeeds subsequently.
Thus the ways a piece of computation fails have to be reified as a family of types as well.
This family of types is defined as \ensuremath{\protect\hyperlink{_5f2f21a6}{\anonymous \kern.5\underscorespace{\mathrel{\not\mapsto}}}} (mutually with \ensuremath{\protect\hyperlink{_5f21a65f}{\anonymous \kern.5\underscorespace{\mathrel{\mapsto}}\kern-\underscorespace\anonymous }}), also in \autoref{fig:CompSeq}.
Similarly, we can prove that
\[ \ensuremath{\identifier{mx}\;\protect\hyperlink{_5f2f21a6}{\mathrel{\not\mapsto}}} \qquad\text{and}\qquad \ensuremath{\protect\hyperlink{R72756e506172}{\identifier{runPar}}\;\identifier{mx}\;\protect\hyperlink{_5f22615f}{\identifier{≡}}\;\protect\hyperlink{N6e6f7468696e67}{\constructor{nothing}}} \]
are equivalent, showing that the reification of \ensuremath{\protect\hyperlink{R72756e506172}{\identifier{runPar}}\;\identifier{mx}\;\protect\hyperlink{_5f22615f}{\identifier{≡}}\;\protect\hyperlink{N6e6f7468696e67}{\constructor{nothing}}} as \ensuremath{\identifier{mx}\;\protect\hyperlink{_5f2f21a6}{\mathrel{\not\mapsto}}} is again accurate.
We are thus entitled to use \ensuremath{\protect\hyperlink{_5f21a65f}{\anonymous \kern.5\underscorespace{\mathrel{\mapsto}}\kern-\underscorespace\anonymous }} and \ensuremath{\protect\hyperlink{_5f2f21a6}{\anonymous \kern.5\underscorespace{\mathrel{\not\mapsto}}}} for stating various properties involving success or failure of decidably partial computation, in particular well-behavedness of bidirectional transformations in the next section.

\section{Putback-based bidirectional transformations}
\label{sec:BX}

We follow the classic (well-behaved) lens approach~\cite{Foster-lenses} to bidirectional transformations, but adopting the variation used by Pacheco~et~al~\cite{Pacheco-putlenses}:
\begin{definition}[lenses]
A (well-behaved) \emph{lens} between a source type \ensuremath{\identifier{S}\;{:}\;\constructor{Set}} and a view type \ensuremath{\identifier{V}\;{:}\;\constructor{Set}} is a pair of functions
\[ \ensuremath{\protect\hyperlink{P707574}{\identifier{put}}\;{:}\;\identifier{S}\;\identifier{→}\;\identifier{V}\;\identifier{→}\;\protect\hyperlink{P506172}{\constructor{Par}}\;\identifier{S}} \qquad\text{and}\qquad \ensuremath{\protect\hyperlink{G676574}{\identifier{get}}\;{:}\;\identifier{S}\;\identifier{→}\;\protect\hyperlink{P506172}{\constructor{Par}}\;\identifier{V}} \]
satisfying the \emph{PutGet} law:
\[ \ensuremath{\protect\hyperlink{P707574}{\identifier{put}}\;\identifier{s}\;\identifier{v}\;\protect\hyperlink{_5f21a65f}{\mathrel{\mapsto}}\;\identifier{s'}} \quad\text{implies}\quad \ensuremath{\protect\hyperlink{G676574}{\identifier{get}}\;\identifier{s'}\;\protect\hyperlink{_5f21a65f}{\mathrel{\mapsto}}\;\identifier{v}} \qquad\text{for all \ensuremath{\identifier{s}},~\ensuremath{\identifier{s'}\;{:}\;\identifier{S}} and \ensuremath{\identifier{v}\;{:}\;\identifier{V}}} \]
and the \emph{GetPut} law:
\[ \ensuremath{\protect\hyperlink{G676574}{\identifier{get}}\;\identifier{s}\;\protect\hyperlink{_5f21a65f}{\mathrel{\mapsto}}\;\identifier{v}} \quad\text{implies}\quad \ensuremath{\protect\hyperlink{P707574}{\identifier{put}}\;\identifier{s}\;\identifier{v}\;\protect\hyperlink{_5f21a65f}{\mathrel{\mapsto}}\;\identifier{s}} \qquad\text{for all \ensuremath{\identifier{s}\;{:}\;\identifier{S}} and \ensuremath{\identifier{v}\;{:}\;\identifier{V}}.} \]

Informally:
Execution of \ensuremath{\protect\hyperlink{P707574}{\identifier{put}}\;\identifier{s}\;\identifier{v}} should produce an updated version of the source~\ensuremath{\identifier{s}} by properly embedding all information of the view~\ensuremath{\identifier{v}} into~\ensuremath{\identifier{s}}.
The \ensuremath{\protect\hyperlink{P507574476574}{\identifier{PutGet}}} law ensures that \ensuremath{\protect\hyperlink{P707574}{\identifier{put}}} does its job properly by requiring that, after \ensuremath{\protect\hyperlink{P707574}{\identifier{put}}} updates a source with a view, \ensuremath{\protect\hyperlink{G676574}{\identifier{get}}} can completely recover the view from the updated source.
The \ensuremath{\protect\hyperlink{G476574507574}{\identifier{GetPut}}} law, on the other hand, ensures that \ensuremath{\protect\hyperlink{P707574}{\identifier{put}}} does nothing more than its designated job by requiring that \ensuremath{\protect\hyperlink{P707574}{\identifier{put}}} performs no update on a source if the view it receives is directly extracted from the source by \ensuremath{\protect\hyperlink{G676574}{\identifier{get}}}.
Note that our definition of lenses is stronger than the one given by Foster~et~al~\cite{Foster-lenses}: our \ensuremath{\protect\hyperlink{P507574476574}{\identifier{PutGet}}} law says that successful computation of \ensuremath{\protect\hyperlink{P707574}{\identifier{put}}} guarantees success of the subsequent computation of \ensuremath{\protect\hyperlink{G676574}{\identifier{get}}}, whereas in Foster~et~al's definition there is no such guarantee; the \ensuremath{\protect\hyperlink{G476574507574}{\identifier{GetPut}}} law is similar.

Various bidirectional programming languages have been built based on the idea of lenses.
Such languages would contain a set of primitive lenses, like those we build by \ensuremath{\protect\hyperlink{I69736f2d6c656e73}{\identifier{iso}\text-\kern-.75\underscorespace\identifier{lens}}}, and a set of combinators which combine smaller lenses into larger ones, like what \ensuremath{\protect\hyperlink{_5f21945f}{\anonymous {\scalebox{.75}[1]{$\leftrightarrow$}}\kern-\underscorespace\anonymous }}~does.
Usually these languages are designed to suggest that what they describe are \ensuremath{\protect\hyperlink{G676574}{\identifier{get}}} programs, but it has recently been argued that the opposite \emph{putback-based} approach should be adopted instead.
The argument is based on the following theorem:
\begin{theorem}[putback is the essence]
Define, for every \ensuremath{\identifier{mx}},~\ensuremath{\identifier{my}\;{:}\;\protect\hyperlink{P506172}{\constructor{Par}}\;\identifier{A}}, a type \ensuremath{\identifier{mx}\;\raisebox{\ht\strutbox}{\hypertarget{_2248}{}}\identifier{≈}\index{_2248@\ensuremath{\identifier{≈}}}\;\identifier{my}} to mean that \ensuremath{\identifier{mx}\;\protect\hyperlink{_5f21a65f}{\mathrel{\mapsto}}\;\identifier{z}} if and only if \ensuremath{\identifier{my}\;\protect\hyperlink{_5f21a65f}{\mathrel{\mapsto}}\;\identifier{z}} for any \ensuremath{\identifier{z}\;{:}\;\identifier{A}}.
Then for any \ensuremath{\identifier{S}},~\ensuremath{\identifier{V}\;{:}\;\constructor{Set}} and two lenses \ensuremath{\identifier{l}},~\ensuremath{\identifier{r}\;{:}\;\protect\hyperlink{L4c656e73}{\constructor{Lens}}\;\identifier{S}\;\identifier{V}} such that
\[ \ensuremath{\protect\hyperlink{L4c656e73}{\constructor{Lens}}\kern.6\underscorespace\text.\protect\hyperlink{P707574}{\identifier{put}}\;\identifier{l}\;\identifier{s}\;\identifier{v}\;\protect\hyperlink{_2248}{\identifier{≈}}\;\protect\hyperlink{L4c656e73}{\constructor{Lens}}\kern.6\underscorespace\text.\protect\hyperlink{P707574}{\identifier{put}}\;\identifier{r}\;\identifier{s}\;\identifier{v}} \qquad\text{for all \ensuremath{\identifier{s}\;{:}\;\identifier{S}} and \ensuremath{\identifier{v}\;{:}\;\identifier{V}},} \]
we have
\[ \ensuremath{\protect\hyperlink{L4c656e73}{\constructor{Lens}}\kern.6\underscorespace\text.\protect\hyperlink{G676574}{\identifier{get}}\;\identifier{l}\;\identifier{s}\;\protect\hyperlink{_2248}{\identifier{≈}}\;\protect\hyperlink{L4c656e73}{\constructor{Lens}}\kern.6\underscorespace\text.\protect\hyperlink{G676574}{\identifier{get}}\;\identifier{r}\;\identifier{s}} \qquad\text{for all \ensuremath{\identifier{s}\;{:}\;\identifier{S}}.} \]
\end{theorem}
The theorem tells us that, when designing a bidirectional combinator, if we can justify the design of its \ensuremath{\protect\hyperlink{P707574}{\identifier{put}}} component, then its \ensuremath{\protect\hyperlink{G676574}{\identifier{get}}} component needs no further justification, since there is no other \ensuremath{\protect\hyperlink{G676574}{\identifier{get}}} that can be paired with the same \ensuremath{\protect\hyperlink{P707574}{\identifier{put}}}.
This is in sharp contrast with the \ensuremath{\protect\hyperlink{G676574}{\identifier{get}}}-based approach, with which the designer needs to choose for each \ensuremath{\protect\hyperlink{G676574}{\identifier{get}}} one or a few possible \ensuremath{\protect\hyperlink{P707574}{\identifier{put}}} strategies to be paired with the \ensuremath{\protect\hyperlink{G676574}{\identifier{get}}}.
This complicates the design as there would be multiple combinators with the same \ensuremath{\protect\hyperlink{G676574}{\identifier{get}}} semantics, distinguished only by differences in their \ensuremath{\protect\hyperlink{P707574}{\identifier{put}}} semantics --- this is rather counterintuitive since the programmer is supposed to think in terms of \ensuremath{\protect\hyperlink{G676574}{\identifier{get}}} instead of \ensuremath{\protect\hyperlink{P707574}{\identifier{put}}} when programming in \ensuremath{\protect\hyperlink{G676574}{\identifier{get}}}-based languages.
Also it is harder to justify the design as to why the set of particular \ensuremath{\protect\hyperlink{P707574}{\identifier{put}}} strategies are chosen, and it may well happen that, after the programmer describes a \ensuremath{\protect\hyperlink{G676574}{\identifier{get}}}, the corresponding \ensuremath{\protect\hyperlink{P707574}{\identifier{put}}} synthesised by the language is not what the programmer wants.
All these problems simply do not exist for the putback-based approach.


\section{\BiGUL\ and its lens semantics}
\label{sec:BiGUL}

Following the putback-based approach, our language \BiGUL\ describes \ensuremath{\protect\hyperlink{P707574}{\identifier{put}}} functions, i.e., updates to a source using a view.
In general, an update proceeds by decomposing the source into several parts to be updated independently~(\autoref{sec:source-update}), and accordingly rearranging the view to match with these parts~(\autoref{sec:view-rearrangement}), until the source and the view are reduced to the extent that atomic operations can be applied~(\autoref{sec:basic-lenses}).
When both the source and the view are lists, there is a powerful aligning operation for synchronising the two lists~(\autoref{sec:list-alignment}).
And we can do case analyses on either the source~(\autoref{sec:source-case}) or the view~(\autoref{sec:view-case}) for describing more flexible update strategies.

In the rest of this section we will present the lens semantics of each of the bidirectional operations mentioned above, and then summarise the whole language in a datatype \ensuremath{\constructor{BiGUL}} and its interpreter to \ensuremath{\protect\hyperlink{L4c656e73}{\constructor{Lens}}} in \autoref{sec:deep-embedding}.

\subsection{Replacing, failure, and skipping}
\label{sec:basic-lenses}

The three most basic lenses are replacing, failure, and skipping.
\emph{Replacing} is applicable when the source and the view are of the same type, and its \ensuremath{\protect\hyperlink{P707574}{\identifier{put}}} semantics is discarding the original source and returning the view as the updated source.

The next lens, \ensuremath{\mathit{caseS}\text-\kern-.75\underscorespace\identifier{lens}}, is for doing case analysis on the source.
The basic idea of the putback semantics of \ensuremath{\mathit{caseS}\text-\kern-.75\underscorespace\identifier{lens}} is to choose from a list of branches the first one that matches the source, and then execute the putback semantics of the lens associated with the chosen branch.
It is, however, difficult to find a \ensuremath{\protect\hyperlink{G676574}{\identifier{get}}} to pair with this \ensuremath{\protect\hyperlink{P707574}{\identifier{put}}}: the obvious \ensuremath{\protect\hyperlink{G676574}{\identifier{get}}} which selects the first branch that matches its source argument does not work, because it may well happen that the updated source produced by \ensuremath{\protect\hyperlink{P707574}{\identifier{put}}} matches a different branch from the original source, so in general we would have to guarantee \ensuremath{\protect\hyperlink{P507574476574}{\identifier{PutGet}}} for \ensuremath{\protect\hyperlink{P707574}{\identifier{put}}} and \ensuremath{\protect\hyperlink{G676574}{\identifier{get}}} coming respectively from any two branches, which is unmanageable.
A more manageable solution is to insert a dynamic check at the end of \ensuremath{\protect\hyperlink{P707574}{\identifier{put}}} to ensure that the updated source must match the same branch as the original source, but in practice this solution is too restrictive to be useful.
We bump right into an obstacle for our very first combinator!

Our solution is to invent a special kind of branches called \emph{adaptive} branches, in addition to \emph{normal} branches.

We might think of a source case analysis as still consisting mainly of normal branches, but now for \ensuremath{\protect\hyperlink{P707574}{\identifier{put}}} we allow the source to match an adaptive branch, which transforms the source such that it matches a normal branch.
More explicitly, the case analysis may be run twice when executing \ensuremath{\protect\hyperlink{P707574}{\identifier{put}}}: if a normal branch is chosen the first time, then the case analysis succeeds, and we execute the \ensuremath{\protect\hyperlink{P707574}{\identifier{put}}} associated with the branch; otherwise, we adapt the source and rerun the case analysis, and must match a normal branch this time.
The corresponding \ensuremath{\protect\hyperlink{G676574}{\identifier{get}}} similarly goes through the same list of branches, but fails immediately if an adaptive branch is matched.

For case analysis on the view, there is still a list of branches, with each of which a lens is associated --- there are no adaptive branches.
We must be more careful when it comes to the view, though:
As we mentioned in \autoref{sec:basic-lenses}, view information must be carefully managed and completely embedded into the source.
When a branch matches the view, the amount of view information that remains to be embedded can actually be reduced.
For example, if there is a branch that matches an integer view which equals zero, then for this branch we may even perform no update on the source as long as we can guarantee that the subsequent \ensuremath{\protect\hyperlink{G676574}{\identifier{get}}} will choose this branch, in which case \ensuremath{\protect\hyperlink{G676574}{\identifier{get}}} can simply return zero --- the information that the view is zero is embedded implicitly in the control flow rather than explicitly in the updated source.
Thus, in the definition of \ensuremath{\protect\hyperlink{C43617365564272616e6368}{\constructor{CaseVBranch}}} below, we use a partial isomorphism on the view type which converts it to a less informative type, instead of just a decidable predicate as in \ensuremath{\protect\hyperlink{C43617365534272616e6368}{\constructor{CaseSBranch}}}:
